## 1. モデルとエフォートの選択

**現状**: `preset: current` のみ。画面の思考量メニューには「モデル（ラジオ: 最新 / GPT-5.6 Sol / GPT-5.5）」と「思考量（スライダー 0..4、段階 3 = 極高）」がある（✅）。

**設計変更の提案（Phase 5 で実装）**:

- `request.json` の `preset` を「effort の段階」に限定し、別途 `model` を任意項目として追加する。

  ```json
  { "preset": "extra_high", "model": "latest" }
  ```

  | `model` | UI ラジオ（ja） | 状態 |
  |---|---|---|
  | `latest`（既定） | 最新 | ✅ 存在確認済み |
  | `gpt-5.6-sol` | GPT-5.6 Sol | ✅ 存在確認済み |
  | `gpt-5.5` | GPT-5.5 | ✅ 存在確認済み |
  | `current` | 操作しない | — |

- 選択操作は「トリガをクリック → メニューを確認 → スライダーにフォーカスして矢印キーで目標段階へ → `aria-valuenow` とトリガのラベルを読み戻して一致確認 → 不一致なら `MODEL_NOT_VERIFIABLE` で送信しない」。すべて DOM / accessibility 操作（CON-008 内）。🔶
- `result.json` に `observedModel` を追加し、`data-message-model-slug`（回答ターンの属性、✅）と照合する。**送信後に slug が要求と食い違えば `warnings` に記録**（回答は取得済みなので失敗にはしない。fail closed の対象は「送信前の確認」）。
- 段階 0/1/2/4 のラベルは `inspect-ui` の拡張（スライダーを一段ずつ動かして読み、**送信せず**元に戻す）で確定してから `PRESET_LABELS` に登録する。

**リスク**: 有料プランの上限（Pro 系モデルの利用回数）に当たると `RATE_LIMITED` で止まる。段階の意味（`medium`/`high` が段階 1/2 のどちらか）は推定なので、確定まで enum を変えない。

## 2. リポジトリを ChatGPT が読めるか

**結論（設計上）**: ChatGPT Web はローカルファイルを読めない。**読ませたい内容はブリッジ側が組み立てて渡す**。渡し方は 3 通り。

| 方法 | 仕組み | 上限（❓ 要計測） | 状態 |
|---|---|---|---|
| A. プロンプト本文に埋め込む | `prompt.md` にファイル内容を fence で貼る | ChatGPT は長い貼り付けを自動で「貼り付けテキスト」添付に変換する。何文字から変換されるか、入力欄の `fill` で同じ挙動になるかは未検証 | 🔶 |
| B. ファイル添付 | 入力欄の「+」→ `input[type=file]` に Playwright `setInputFiles` | 添付数・サイズ・拡張子の制限（`.ts` が許可されるか、`.zip` は？）を計測 | 🔶 DOM 操作なので許容範囲 |
| C. 公開 URL | 公開 GitHub リポジトリの URL を貼り、ChatGPT のブラウジングに任せる | 非公開リポジトリは不可。ブラウジングの有無はアカウント設定依存 | ❓ |
| D. ChatGPT の GitHub コネクタ | アカウント設定で接続する機能 | ブリッジからは操作しない（アカウント設定の変更は範囲外）。人間が接続済みなら「コネクタを使って」と書くだけ | ❓ |

**「読めないなりの活用」= コンテキストバンドル**（Phase 5 で `bundle` サブコマンドを提案）:

```powershell
chatgpt-bridge bundle --root S:\Projects\PixivVault --include "src/**/*.ts" --exclude "**/*.test.ts" --max-bytes 200000 --out .\runtime\requests\<id>\context.md
```

- 出力: ファイルツリー + 各ファイルを `path` 見出し付き fence で連結した Markdown。`git diff` / 特定コミットの差分だけを入れるモードも用意する
- 秘密情報の混入防止: `.env`、鍵、`node_modules`、`.git` を既定で除外し、既存の `redact.ts` のパターンで走査して**該当があれば生成を拒否**する（SEC-*）
- `prompt.md` から `{{context}}` で参照する簡単なテンプレート、または添付方式（B）に切り替えるフラグ

## 4. API 的に使えるか（えまきのこ / たぐきのこ への組み込み）

**率直な所見**:

| 観点 | 評価 |
|---|---|
| 応答時間 | 1 往復 20〜60 秒以上（起動 5 秒 + 推論 + 安定待ち 1.5 秒 + 終了）。**対話 UI に埋め込む用途には遅すぎる** |
| 同時実行 | 1 件ずつ。複数ユーザ / 複数アプリからの同時要求はキューで直列化するしかない |
| 可視ブラウザ | 実行中は Chrome ウィンドウが開く。デスクトップアプリの裏で黙って動く体験にはならない（ヘッドレスは不採用、CON-005） |
| 安定性 | UI 変更で壊れる（`DOM_CHANGED`）。API のような後方互換性は無い |
| 規約 | ブリッジは個人の ChatGPT アカウントの画面操作である。**製品に組み込んで第三者に提供する形は、規約上の問題が無いと断言できない**（絶対条件: 断言禁止）。少なくとも「自分の PC で、自分のアカウントで、自分のために」の範囲で使う前提 |

**向いている使い方**: 人間が起動する**バッチ / 非同期ジョブ**。

- えまきのこ: 「選択した作例 50 件の説明文を生成」ボタン → リクエストをキューに投入 → ブリッジが順に処理 → 結果をアプリが取り込む。ユーザには「処理中（ブラウザが開きます）」と見せる
- たぐきのこ: タグ候補の提案をバッチで事前計算し、アプリ内検索は事前計算結果を使う（検索のたびにブリッジを呼ばない）
- 作例検索そのものをチャットに任せるのは、レイテンシと直列制約から**非推奨**。検索はアプリ内のインデックスで、生成だけブリッジで

**向いていない使い方**: リアルタイム対話、複数ユーザ同時、無人サーバ運用、配布アプリへの同梱。

## 5. 他プロジェクトのオーケストレータから使う

CON の範囲（ローカル、サーバ / DB を持たない）で実現できる 3 段階。

### 5a. いますぐ: CLI をそのまま呼ぶ（Phase 4 で可能）

```powershell
node S:\Projects\chatgpt-web-bridge\dist\cli\main.js run --request <path>
```

exit code と `result.json` で判断する（`docs/20-COMMAND-REFERENCE.md` §4d の判断ルール）。オーケストレータ側で requestId を生成し、リクエストディレクトリを作る。

### 5b. Phase 5: `npm link` でグローバルコマンド化 + 契約の固定

- `chatgpt-bridge` を PATH に置く（`npm link` または `npm install -g <repo>`）
- `request.json` / `result.json` のスキーマを `schemas/` からコピー可能にし、他プロジェクトは **スキーマだけ**に依存する（コードは依存しない）
- `--json` フラグで標準出力を JSON 1 行（`result.json` と同じ内容）にし、パースしやすくする

### 5c. Phase 6 候補: ファイルキュー + ワーカー

```
<queue>\
  pending\<requestId>\request.json + prompt.md   ← 他プロジェクトが置く
  running\<requestId>\                          ← ワーカーが移動
  done\<requestId>\result.json + response.md    ← 完了
  blocked\<requestId>\                          ← exit 3（人間待ち）
```

```powershell
chatgpt-bridge worker --queue <dir> [--once]
```

- ワーカーは `pending` を古い順に 1 件ずつ `run` と同じ経路で処理する（直列・単一プロセスの条件は維持）
- exit 3 が出たら **キュー全体を停止**して人間を待つ（後続を自動で流さない）
- HTTP サーバは作らない（禁止事項）。オーケストレータはディレクトリを監視する
- Claude Code / Codex から使う場合はこのディレクトリ規約を `SKILL.md` にして渡せば、他 PJ 側の変更が最小になる
