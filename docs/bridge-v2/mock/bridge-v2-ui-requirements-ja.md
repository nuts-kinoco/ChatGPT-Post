# Bridge v2 UIモック 要件対応

2026-10-03 · レビュー版 · 非実行

## 方針

既存の第一候補「縦のステータスドック」をそのまま主役にしています。280 × 380 px、Bのマーク、状態 → 依頼名 → 宛先 → 理由 → 完了結果 → 停止・詳細の順序と、既存の色・角丸を継承しました。6案を新しく作り直していません。

細かい情報は隣の詳細パネルへ展開します。1920 × 1080を想定し、対になるカード、承認方式、操作ボタンは同じグリッドで幅・高さを揃えています。デスクトップでは詳細の本文だけがスクロールし、操作は下端に残ります。狭い画面では縦に並びます。ブラウザ描画は後述の制約により未検証です。

## ファイル

- **bridge-v2-interface.html**：外部依存のない単一HTML。オフラインで開ける、画面内の状態だけを動かすモック
- **ui-task-fixture.json / ui-task-fixture.md**：初期表示と一致する設計用データ。mode=design_fixture、パス・コマンド許可は空。実行用ではありません
- **validation-results.json**：状態ロジック20件の検証結果

実際の接続、送信、CLI起動、Windows操作、リポジトリ編集、永続的な許可、外部ストレージ保存はありません。ページを再読み込みすると画面内の状態は破棄されます。

## 要件と画面の対応

| 要件 | 画面・操作 |
|---|---|
| JSON + MDの受け渡し | 「依頼の内容」で両方を表示。UTF-8の生バイトに対してSHA-256を計算 |
| 内容に結びつく承認 | 「承認と許可」でTaskSpecハッシュ、記録ID、ポリシー版、期限、開始回数を表示 |
| manual / automatic / bypass | 同じ寸法の3ボタン。初期選択は事前許可（bypass）の**設計例**。実際の許可は未設定 |
| bypassの境界 | 省略するのは範囲内の依頼ごとの確認。ハッシュ、許可範囲、期限、重複検証は継続 |
| 編集後の失効 | MD、送信先、承認方式の変更で承認を失効。受理済みIDの変更内容は競合として保留し、「新しいIDで準備」後に再照合 |
| 許可範囲 | repo、agent/model、パス、編集、コマンド、期限、利用回数を表示。fixtureには実行許可なし |
| セッション上限 | 件数、時間、予算の設定例。実際の予算・課金はなく、¥1,000は見積価格ではない |
| 9つの実行状態 | received / awaiting_approval / approved / running / cancel_requested / cancelled / succeeded / failed / unknown |
| 二重実行防止 | 「同じ内容を再受信」は追加開始せず、既存記録を表示 |
| 同一IDの競合 | 「同じIDで内容を変更」は競合を拒否。元の受理済み記録は上書きしない |
| 停止と復旧 | 停止要求と停止確認を分離。「復旧の確認」は記録を照合するだけ。unknownで再実行しない。未確定の実行は別の保留フラグで保持し、編集・新ID・方式変更でも解除しない |
| 期限・取り消し・緊急停止 | 承認の失効、新規開始の保留、停止要求の表示を再現。期限切れでも進行中の実行は保持し、取り消し時は停止確認待ちにする。完了後の制限変更では確定済みの結果とACKを保持。終了済みの依頼は内容変更不可で、別内容には新しいIDを用意 |
| 3つの宛先 | 通常のChatGPTチャット / Claude CLI / Codex CLI。すべて未接続の表示例。ChatGPTチャットは既存ブラウザ経路を指す。Work / dot向けMCP Eventsは別の将来候補で、この宛先には含めない |
| 配達と実行の分離 | チャット認証待ちは配達の状態。CLIへ停止を伝播しない。CLIの利用可否も勝手に確認済みにしない |
| 確実な受け渡し | 発行 → 受信ACK → 開始確認 → 終了結果 → 結果ACKを別表示。ID・ハッシュ・run IDで紐づける設計 |
| 成功と受領とmergeの分離 | 実行成功だけで結果受領・merge済みとしない。結果ACKは実行状態を変えない |
| 証跡 | actual_agent/model、run ID、コマンド、テスト、終了コード、差分、ログの未取得を明記。合成状態を実観測と扱わない |
| 接続診断 | 「復旧の確認」の折りたたみ。設定済み / 実機確認済み / 認証必要 / 不明を区別 |
| 実行前確認 | 「承認と許可」の折りたたみ。モデル、推論設定、パス、コマンド、課金方式、見積根拠、確認時刻 |
| 利用枠 | 値は不明。automatic / manual / unknown、対象時間枠、確認時刻を区別。実機取得は未検証。取得不能なら本人に確認 |
| 依存するジョブ | 「実行の記録」の折りたたみ。実装 → 監査 → テスト。依存待ち・前段失敗による保留と排他ロックを分離 |
| 入力経路 | チャット / GitHub等は検討中。GitHub pushの成功を受信ACKにしない。GitHubだけでチャットへ送信・起動できるとは扱わない |

## 試し方

1. 初期表示の「範囲を照合する」で、ハッシュに結びつくデモの承認記録を表示
2. 「開始状態へ」→「停止を求める」で、実行中と停止要求済みの違いを確認
3. リセット後、「依頼の内容」でMDを編集。ハッシュ変化と承認失効を確認
4. 下部の「表示シナリオを試す」を開き、「新しいIDで準備」して再照合
5. 「状況不明」→「復旧の確認」で、記録を照合しても再実行しないことを確認
6. 「完了」→「実行の記録」で、結果ACK前後の違いを確認

下部のシナリオ選択は検証用です。任意の状態へ直接切り替えるため、実際のプロトコル遷移を観測した履歴ではありません。

## 検証

- JavaScript構文検査：通過
- HTMLのID重複・JavaScript参照先：問題なし
- 外部画像・フォント・スクリプト・送信フォーム：なし
- ネットワーク呼び出し・永続保存・実行API：なし
- SHA-256：空文字、ASCII、日本語UTF-8をNode標準実装と照合
- 状態ロジック：承認、開始1回、編集失効、新ID、重複、競合、停止、unknown、期限切れ、取り消し、緊急停止、ACK、宛先分離を含む20件通過
- 初期TaskSpec：同梱v2 schemaに適合
- ブラウザ描画：未確認。ローカルChromiumは環境のsocket制限で起動不可、クラウドブラウザはfile://を許可しないため中止。制限回避はしていません

「表示用レコード」はUI専用の参考データで、契約上のResultRecordとして受信させるものではありません。正規のJSON Schemaと実行結果の例は、別のv2プロトコル資料が基準です。
