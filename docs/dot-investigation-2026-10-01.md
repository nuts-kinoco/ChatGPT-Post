# dot（ChatGPT の個人アシスタント）をブリッジから使えるか: 調査結果（2026-10-01）

依頼元: EMAKINOCO-Windows オーケストレータ（PO 承認済み）。方法: 専用プロファイルのブラウザで画面と DOM を**読み取るだけ**（メッセージは一度も送っていない。Codex 不使用）。分かったこと／分からないことを分けて書く。

## 結論
- **入口は特定でき、今のプロファイルでそのまま開ける。** 送信まで含む実装は「中」規模。ただし**完了判定・複数返信・承認画面は実際に送らないと確定しない**ため、実装前に PO の許可を得た小さな実送信試験（1〜2 回）が要る。
- ブリッジの前提（1 依頼＝新しい会話に 1 回の回答）と dot（常設の 1 本のスレッドに、短い返信が複数回来る）は構造が違う。`target: dot` を足すだけでは済まない。

## 項目別

|---|---|---|
| 1 入口 | サイドバーの「Your dot」ボタン（`data-sidebar-destination="builtin:orbit"`、リンクではなくボタン）。クリックで `https://chatgpt.com/dots/home` → `https://chatgpt.com/dots/<uuid>` へ遷移。URL へ直接 goto しても同じ。専用プロファイルのログインのまま操作できた。同じサイドバーの他の組込み先: home / space / automations / customize | 会話は 1 本の常設スレッドに見え、「新しいチャット」に相当するものは確認できない（複数スレッドの有無は未確認） |
| 2 完了判定 | メッセージの DOM が通常チャットと別: `article.message-row`（自分の発言は `self` クラス付き、連続する返信は `grouped-previous`）、本文 `div.message-body`、`data-message-id`、既読表示。**通常チャットの `data-message-author-role` / `data-turn` は無い**ので現行の assistantTurn/userTurn 検出は一致しない（新しいセレクタが要る）。入力欄は contenteditable、案内文は「メッセージ」 | 生成中の表示（停止ボタン等）、途中経過の出し方、完了の合図。**送らないと見えない** |
| 3 成果物 | 添付はメッセージ内の `button[aria-label="<ファイル名>を開く"]`。クリックで右側にビューアが開き、ファイルの中身（md は整形表示）、`ダウンロード` ボタン、`ビューアーを閉じる` ボタンがある。取得方法は 2 通り: (a) ダウンロードボタン＋ Playwright の download イベント、(b) ビューアの DOM を既存の htmlToMarkdown で読む（ダウンロード不要） | (a) は 2026-09-15 に画像ビューアの保存ダウンロードで Chrome が自動操作下でクラッシュした前例（A-092）があり、dot で安全かは未検証。HTML ファイルの表示（整形かソースか）、ZIP/patch の扱いは未確認。現行の artifacts/images 経路は `<img>` 専用で流用できない |
| 4 コネクタ承認 | 今回の読み取りでは承認画面は出ていない。dot は GitHub の非公開リポジトリを既に読めている様子（過去の会話内容から） | 承認画面が出る条件と見た目。出た場合は無人では止まるので、既存の blockingDialog / CHALLENGE と同じく**止めて人間に渡す**設計が妥当（検知セレクタは実物を見てから） |
| 5 長い作業の待ち／追記／collect | 会話 URL は固定（`/dots/<uuid>`）で、常に「追記」になる。追記の受理判定は A-191 で長文の折りたたみに対応済み（dot の DOM では別途要確認） | **dot は 1 つの依頼に対して複数の短い返信と添付を別メッセージで返す**（実際の履歴で確認）。「基準後の唯一の回答」を前提にする collect の `COLLECT_REPLY_AMBIGUOUS` 等と相性が悪い。「自分の発言の後〜静止まで全部」というモデルに変える必要がある。dot 側から自発的に来る通知・返信もあり得る |

## 規模の見積もり
- 小: 入口への遷移、メッセージのセレクタ追加、テキストの送信、固定の締めの合図（例「以上で完了」）＋静止時間での完了判定、返信の読み取り（添付はビューア DOM から md として取得）。
- 中: 複数メッセージ返信と添付を結果にまとめる（result の拡張）、collect/回復の再設計、承認画面・ブロック表示の検知、ダウンロード方式の安全確認。
- 大: dot が自走して長時間作業・通知・自発メッセージを出す場合の完全な無人運用、承認を挟むコネクタ作業の自動化。
- 総合: **MVP（送信＋合図付き完了待ち＋テキストと md 添付の取得）は「中」。**無人運用まで含めると「大」。

## 危険
- **dot は実際の操作（GitHub 参照、Codex タスクの起動）をする。** ブリッジ経由の依頼でも、PO の知らない所で Codex 枠・外部サービスを使う可能性がある。依頼文で「Codex タスクは起動しない」「読み取りのみ」を明示する運用が要る。
- **PO の常設スレッドに混ざる。** 送信すると PO 本人が打ったように表示され、dot の記憶・文脈に影響する。PO が手で使っている時と衝突し、返信の取り違えが起きる（requestId をメッセージ先頭に入れる運用で緩和）。
- **プロファイル競合:** 専用プロファイルは 1 つのブラウザしか開けない（現行と同じ制約）。dot 用に別のウィンドウを増やさない。
- **規約・Cloudflare:** dot は自動操作に対する扱いが未確認の新機能。通常チャットと同様に Cloudflare の確認が出る可能性があり、ブリッジは自動突破しない（人間が通過）。アカウントへの影響が出る前に、少量の試験で様子を見る。
- **機微な内容:** 読み取りに使った画面にも PO の私的な会話が表示されていた。調査用の保存物（DOM・スクリーンショット）は共有しない。

## 次の一手（提案）
1. PO の許可を得て、dot に**無害な 1 通**（例: requestId 付きで「ok とだけ返して」。Codex は起動しないと明記）を送り、生成中の表示・完了の合図・既読・返信数を観察する（1 回）。
2. 添付の返信を依頼し、ビューア経由の取得と download イベントの安全性を 1 回確認する。
3. その結果で規模を確定し、実装するかを決める。

## 追記: 実送信試験の結果（2026-10-01、PO 許可済み・2 通のみ）
送信した内容: (1) 先頭に「【chatgpt-bridge からの自動送信テスト / requestId: …】これはブリッジ（自動操作）から送っています。PO 本人の入力ではありません」と明記し「ok とだけ」と依頼。(2) 同様に明記して、3 行の Markdown `bridge_test.md` を添付で返すよう依頼。どちらも Codex 起動・外部操作はしないと明記。dot のスレッドにはこの 2 通と返信（「ok」「添付しました」＋ `bridge_test.md`）が残っている。

### 観察できたこと（確定）
- **送信**: 入力欄は contenteditable。テキストを入れると「送信」ボタンが有効になり、押すと約 0.2 秒で自分の行（`article.message-row.self`）が増える。送信後、入力欄は空、「送信」は無効に戻る。停止ボタンや `aria-busy` は出ない。
- **進行表示**: 自分の発言の下の状態表示が「**配信済み**」→（約 1〜2.5 秒で）「**既読 HH:MM**」と変わり、続けて「**dot is typing…**」（文字列 `typing…`）が出る。画面上は本文の末尾テキストに現れる。typing が消えた約 0.4 秒後に返信の行が出る。
- **返信の数と所要時間**: 「ok」の依頼は約 11 秒で返信 1 行。添付の依頼は typing が約 26 秒続き、**返信 1 行（本文「添付しました」＋添付チップ 1 件）**。今回は 2 回とも返信は 1 メッセージだった（過去の履歴では 1 依頼に複数メッセージの返信があった。複数になるかは依頼内容次第）。
- **完了の合図**: 「typing が消えた」＋「自分の行より後に dot の行（`article.message-row`、`self` なし）が出た」＋一定時間（今回は 25 秒）変化なし、で判定できた。確実な合図としては依頼文に末尾の合図（例「以上で完了」）を入れるのが無難。
- **添付の取得（ビューア）**: 添付チップ `button[aria-label="<ファイル名>を開く"]` を押すと右側にビューアが開き、md は `div.MarkdownRoot-*` に整形表示される（`data-testid="viewer-header"` あり）。DOM から読む場合は HTML → Markdown 変換が要る（整形表示なので元のバイト列とは一致しない）。
- **添付の取得（ダウンロード）**: ビューアの「ダウンロード」ボタン（`aria-label="ダウンロード"`）→ Playwright の `download` イベントで取得でき、**811 ms で完了、保存内容は元ファイルと完全に一致**（`# bridge test\n自動送信テストです\n- ok\n`）。**ブラウザのクラッシュは起きなかった。** 画像ビューアで 9/15 に起きたクラッシュ（A-092）の再現はなし。
- **コネクタ承認画面**: 今回の 2 通では出なかった（GitHub 等を使わせない依頼だったため）。承認が絡む依頼で出るかは未確認。

### まだ分からないこと
- 大きなファイル、HTML、ZIP、複数ファイルのダウンロード（今回は 3 行の md 1 件のみ）。
- 複数メッセージで返信する依頼での完了判定、dot が自発的に出すメッセージとの区別。
- GitHub・Codex を使う依頼での承認画面の有無と見た目。
- 「dot is typing…」の安定した検知セレクタ（今回は本文末尾の文字列でのみ観測。DOM 要素の特定は未実施）。

### 規模の見直し
- ダウンロードが安全に使えると分かったので、成果物の取得は DOM 読みを避け、**ダウンロード方式を第一候補**にできる（見積もりの「中」の項目が小さくなる）。
- MVP（送信 → `配信済み/既読/typing…` と新しい dot の行による完了待ち → テキスト返信 → 添付のダウンロード）は **「中」のまま、ただし不確実性は下がった**。無人運用（承認画面・複数返信・自発メッセージ）は「大」のまま。
