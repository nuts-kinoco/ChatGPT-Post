# 22. ブリッジのベストプラクティス（プロンプト・運用・知見管理）

作成: 2026-09-15（Phase 5）。PO 要望「ブリッジのベストプラクティスを見極める」への回答。実測（`docs/live-results/`）に基づく部分と、まだ仮説の部分を分けて書く。

## 1. ブリッジが得意なこと / 不得意なこと（実測ベース）

| 用途 | 評価 | 根拠 |
|---|---|---|
| 独立したコードレビュー（1〜数ファイル） | **得意** | CX-01: 仕込んだ 3 件を 3/3、誤検出 0、除外理由も妥当（51 s） |
| 添付ファイルの正確な参照 | **得意** | FL-01/04: 57 k 文字の 777 行目まで正確 |
| 調査・要約（web 検索付き） | 得意 | R-012: 8.9 KB、脚注 URL 付きを 109 s で取得 |
| セカンドオピニオン（設計判断、リスク洗い出し） | 得意（仮説） | リポジトリ全体は見えないので「判断材料を bundle で渡す」前提 |
| 実装パッチの生成（1 ファイル） | **得意** | CX-05: unified diff が `git apply --check` を通過し 3 バグすべて解消 |
| 対話的な作業（多段のやり取り） | 可（遅い） | `newChat: false` で同じ会話に追記できる（EX-03、25 s/往復）。自動化するなら 2〜3 往復まで |
| リアルタイム応答 | 不得意 | 1 往復 28〜66 s |
| 画像生成の受け取り / 画像の説明 | 得意 | MM-02: 1536×1024 PNG を 34〜48 s で取得。MM-01: 画像添付から説明 + タグ |
| バッチ分類（JSON Lines） | 得意 | EX-08: 30 件 70 s、30/30 有効、4〜8 タグ |

## 2. プロンプトの原則（ブリッジ向け）

ChatGPT Web はローカルの何も見えない。**プロンプトだけで完結する**ように書く。

1. **requestId を先頭に書き、回答にも書かせる** — 回答の取り違えを機械的に検出できる（ブリッジの本文検証とは別の保険）
2. **役割・入力・出力形式を 3 行で固定する** — 例: 「あなたは独立レビュアです / 入力は添付の `inventory.ts` / 出力は Markdown、各指摘は `メソッド名・行・入力例・unified diff`」
3. **「分からないときは分からないと書け」「作らない」を明記する** — CX-01 では「疑ったが除外」の節が有用だった
4. **長い材料は添付、指示は本文** — 本文は 20,000 文字上限、添付は正確に読まれる。bundle で作った `context.md` も添付
5. **結論を先に、根拠を後に書かせる** — `response.md` を人が斜め読みするときと、後で索引を作るときの両方で効く
6. **1 リクエスト 1 目的** — 「レビューして、ついでにリファクタ案も」は分ける。回答が長いほど抽出・検証・要約のコストが増える
7. **思考量は用途で固定する** — 1 ファイル規模のレビューは `medium` で `extra_high` と同品質（CX-06: 50 s vs 91 s、どちらも 3/3）。調査・横断的な設計判断は `high`〜`extra_high`。定型変換・分類は `instant` / `medium`。`pro` は週次上限を消費するので「他で解けなかったもの」だけ
8. **モデル指定は必要なときだけ** — 既定（`current` = 最新）で十分。比較実験のときに `gpt-5.5` 等を明示
9. **秘密情報は最初から入れない** — ブリッジは拒否するが、拒否されてから直すより、bundle の `--exclude` とプロンプトの書き方で先に避ける

## 3. 再利用できるプロンプトの型（`prompts/`）

これまで AGY / Codex / サブエージェントに依頼していた「独立した」作業は、同じ MD をブリッジに流せる。リポジトリを見る必要があるものは bundle を添付して独立化する。

| ファイル | 用途 | 渡すもの |
|---|---|---|
| `prompts/second-opinion.md` | 設計判断・方針のセカンドオピニオン | 判断材料（背景、選択肢、制約）を本文に。必要なら設計文書を添付 |
| `prompts/code-review.md` | 機能バグ中心のレビュー（CX-01 の型） | 対象ファイルを添付 |
| `prompts/bug-hunt-bundle.md` | 複数ファイル横断の不整合探し | `bundle` の出力を添付 |
| `prompts/patch-request.md` | 修正パッチを unified diff で要求（CX-05 用） | 対象ファイル + 期待動作 |
| `prompts/research-brief.md` | 調査（公式情報と推測の区別を強制） | 質問と「何が分かれば十分か」 |
| `prompts/classify-batch.md` | 分類 / タグ付けをバッチで（えまきのこ / たぐきのこ想定） | JSON Lines の入力を添付、JSON のみで返させる |

各テンプレートは `{{requestId}}` `{{目的}}` などのプレースホルダを持ち、呼び出し側（Claude Code / Codex / 人間）が埋めて `prompt.md` にする。

## 4. Qwen（ローカル LLM）の代替になるか

| 従来 Qwen に任せていたこと | ブリッジでの扱い | 状態 |
|---|---|---|
| テキスト分類・タグ候補生成（Danbooru タグ等） | `classify-batch.md` でバッチ化。30 件で 70 s、全件有効 | ✅ EX-08 |
| 説明文生成 | 同上 | ✅（同型） |
| 画像からの説明 / タグ推定 | 画像添付（MM-01）。25 s で説明 + タグ 5 | ✅ |
| NSFW を含む素材のタグ付け・画像生成 | **ChatGPT の利用ポリシーで拒否される領域**。ブリッジは拒否をそのまま返す（回避しない）。どこまで拒否されるかは「観測」としてテストできるが、ローカル LLM の完全な代替にはならない | ⛔ 回避不可 / 観測は可 |
| オフライン・無料・無制限 | 代替不可（利用上限、可視ブラウザ、規約） | — |

結論: **SFW のテキスト処理はほぼ代替可能（品質は上）**。NSFW とオフライン要件は Qwen を残す。

## 5. 出力（`response.md`）の知見管理

### 5.1 保存規約

- 生データは `runtime/requests/<requestId>/`（Git 管理外）。**消さない**（`usage` の台帳でもある）
- 知見として残す価値があるものだけ `knowledge/` に**要約して**移す。原文はコピーせず requestId で参照する

```
knowledge/
  INDEX.md                      … 1 行 1 件: 日付 | 種別 | タイトル | 要点 1 文 | requestId | 状態
  2026-09/
    2026-09-15-inventory-review.md
    2026-09-15-pro-usage-limits.md
```

各ノートの先頭に frontmatter:

```yaml
---
requestId: 20260915T071252Z-7a60f691
kind: review | research | second-opinion | classify | other
preset: high
model: latest
status: adopted | rejected | pending
tags: [inventory, pagination]
---
```

本文は「結論（3 行）→ 採用したこと → 採用しなかったことと理由 → 原文の場所」。**原文の丸写しはしない**。

### 5.2 コンパクション規則（放置すると膨らむ問題への対策）

| タイミング | 作業 | ルール |
|---|---|---|
| 各リクエスト後 | `INDEX.md` に 1 行追加するか、追加しないと決める | 追加しないものは何もしない（`runtime/requests` に残るだけ） |
| 週 1 回 | `knowledge/<月>/` を見直し、`status: rejected` と `pending` 30 日超を 1 行に圧縮して `INDEX.md` だけに残す | ノート本体は削除、requestId は残す |
| 月 1 回 | `INDEX.md` の同じ tag を 1 段落の「まとめ」に統合し、`knowledge/SUMMARY.md` を更新 | SUMMARY は 200 行以内。超えたら古い月から落とす |
| 四半期 | `runtime/requests/` の 90 日超を `runtime/archive/<yyyy-mm>.zip` に移す | `usage` は移動後の分を数えない（週・日の窓なので実害なし） |

Claude Code / Codex がコンテキストに読むのは **`knowledge/SUMMARY.md` → 必要なら `INDEX.md` → 必要なノート 1 件** の順。原文 `response.md` は最後の手段。

## 6. CLI と MD を行き来する利点を最大化する

- **CLI 側**（Claude Code / Codex / オーケストレータ）: requestId 生成、bundle、request.json、`run --json`、exit code 判定、`usage --json` の事前確認。人間は関与しない
- **MD 側**（人間 / 後続の LLM）: `prompt.md` はテンプレートから、`response.md` は知見ノートへ。両方とも Git や Obsidian で扱える
- 行き来の接点は **`request.json` の 1 ファイル**に固定する。他 PJ は schema だけに依存する（`schemas/request.schema.json` をコピー）
- Claude Code から使うときの型: `SKILL.md`（Phase 6 で作成）に「`usage --json` → bundle → request 作成 → `run --json` → exit 判定 → `knowledge/INDEX.md` 追記」の 6 手順を書く
