# 結論

**全面書き直しは不要です。ただし、現行の`run`を複数起動できるようにするだけでは、今回の要求を安全に満たせません。**

推奨するのは、既存の状態機械・ブラウザ操作・抽出・契約検証を実行部として残し、その上に、**永続的な依頼受付、所有権管理、送信証跡、回収、成果物確定、配送を担当するジョブ管理層**を追加する構成です。

今回、最も重要な設計変更は次の三点です。

1. **CLIの終了、実行担当の終了、ChatGPT上の生成終了、回答の永続化完了、呼び出し元の受領を別々に扱う。**
2. **送信状態が不明なジョブを再送するのではなく、送信済みの可能性を保持したまま回収・照合する。**
3. **「現在開いている会話から取得できた回答」ではなく、「保存済みの依頼との対応を検証した回答」だけを配送する。**

現行daemonはブラウザを常駐させますが、`RunController`は呼び出しCLI内で動きます。また、`GENERATION_TIMEOUT_ACTIVE`も状態機械上は`FAILED`になり、観測を終了します。したがって、**ブラウザの常駐化は実現していますが、ジョブのdurable化はまだ実現していません。** 

**最終推奨構成は「単一のジョブ管理サービス＋そのホストのローカルSQLite＋各マシンのブラウザ担当」です。** SQLiteをSMB等へ置いて複数マシンから直接操作する構成は採用しません。最初は同一マシン・並列数1で導入し、回収と永続化の安全性を確認してから並列化します。

# 3. 危険箇所：並列化前に直すべきもの

## 3.1 最優先：会話URLの形式確認と、依頼への対応確認が混同されている

`observeLoop()`は、現在のURLがChatGPTの会話形式なら、その都度`this.conversationUrl`を上書きします。**最初に束縛した会話と現在の会話が同一かを比較していません。** 

一方、完了判定はassistant件数やstreaming状態を使い、抽出は`extractLatest()`でその時点の最新assistantを取得します。依頼IDや対応するuserターンは検証しません。

したがって、たとえば次の経路が成立します。

```text
依頼Aを会話Aへ送信
  → Pageが会話Bへ遷移
  → Bのassistant件数がbaseline＋1に一致
  → Bの本文が安定
  → conversationUrlもBへ上書き
  → Bの回答を依頼Aのcompletedとして保存
```

補助検証では、この観測・抽出結果をフェイクポートから返すと、現行controllerは実際に`COMPLETED`へ進みました。生成された結果JSONも添付の`result.schema.json`を通りました。

**修正方針：期待する会話の束縛は不変にし、現在URLは観測値として別扱いにする。** 新規会話でまだ確定URLがない期間も、最初に見えた会話URLを無条件で採用してはいけません。後述するuserターンとの対応確認が必要です。

さらに、保持している`sendButton`や最新ターンはPlaywrightのLocatorです。Locatorは使用時にDOMを再検索するため、変数へ保存しただけでは、当初確認した要素への固定にはなりません。([Playwright][1])

## 3.2 既存queueの復旧は、複数workerで安全ではない

`recoverRunning()`は`running/`配下を列挙し、担当プロセスや所有トークンを確認せずに移動します。`result.json`がなければ`pending/`へ戻します。

補助検証では、worker Aのrunnerを実行中のまま待機させ、別途`recoverRunning()`を呼ぶと、Aの処理中ディレクトリが`pending/`へ移動しました。その後Aは終端ディレクトリへの移動に失敗しました。

markerによって二重送信を止められるケースがあっても、**入力・出力ディレクトリを実行中に動かすこと自体が危険**です。別`runtimeDir`のworkerが同じqueueを見る場合には、markerの共有も保証されません。

**当面はqueue全体の単一管理者を保証し、durable化後はディレクトリ移動ではなくDB上のclaimに置き換えるべきです。**

## 3.3 ACTIVE timeoutは「回答を失わない」修正にはなっていない

`GENERATION_TIMEOUT_ACTIVE`の追加は、呼び出し側への注意喚起としては有効です。しかし実装上は、通常timeoutと同じく観測停止・失敗結果保存・ブラウザclose／detach・lock解放へ進みます。

daemon利用時にはブラウザ自体が残る可能性がありますが、**回答を回収する担当は残りません**。さらにlock解放後は、keepaliveや次のコマンドがそのPageを操作できてしまいます。

また、`streaming === false`は「生成が確実に失敗した」ことの証明ではありません。状態を観測できなかった、表示が変わった、切断中だった可能性と区別すべきです。

## 3.4 抽出済み本文が、まだメモリ上だけにある時間が長い

現在は本文抽出後、画像取得を実行し、それが終わってから`WRITE_RESPONSE_MD`へ進みます。画像取得のtimeout時にも、abort後に元のPromiseの終了を待ちます。

一方、画像取得側のページ内`fetch`には、そのAbortSignalが渡されていません。Node側でabortしても、ページ内処理の停止は保証されません。

このため、「本文は取得できたが、画像処理中の停止で本文も保存できなかった」という窓があります。

**本文の検証済みスナップショットを先に永続化し、画像・trace・設定復元を待たせない構造が必要です。** 最終的な`completed`を遅らせることと、取得済み本文の退避を遅らせることは別問題です。

## 3.5 正常完了側の`result.json`書込失敗は、emergency fallbackを通らない

A-113／A-114のfallbackは有用ですが、`WRITE_RESULT`のcatchには次の分岐があります。

```ts
if (!this.state.terminal)
  return { type: "WRITE_FAILED", file: "result", cause };
```

正常完了直前の`WRITING_RESULT`は非終端なので、この分岐に入り、fallbackへ進みません。その後の状態機械も`writesResult: false`で終了します。

補助検証でも、正常抽出後の`writeResult`を失敗させると、呼出回数は1回、`RunOutcome.result`はnullでした。

これは、fallbackを増やせばdurableになるという話ではありません。**MDが存在し、結果確定だけ失敗した状態を、次回起動時に正しく確定できる仕組み**が本体です。

## 3.6 keepalive・Page修復・closeは、ジョブ所有権に参加していない

keepaliveはlockファイルの存在を確認しますが、lockを取得していません。確認後にCLIがlockを取得できるため、再確認を増やしても競合窓はなくなりません。コードにも、この競合窓が残ることが明記されています。

終了処理にも、文書と実装の差があります。

* `BrowserSession.close()`は非daemon経路で最初のcloseがtimeoutすると、再度`ctx.close()`を上限なしで待ちます。
* daemon経路のtrace停止・CDP切断にも、この関数内では明示的な上限がありません。
* daemon側の`shutdown()`は、contextのcloseがtimeoutしてもstateファイルを削除して終了します。

したがって、**永久にlockを保持するケースと、実ブラウザが残っているのに不在扱いするケースの双方を排除できていません。** 

また、`withTimeout()`はPromiseを待つ期限を制限するだけで、元の操作をキャンセルしません。期限切れ後の古い操作が新担当のPageや成果物へ作用しない設計が必要です。

## 3.7 `profileId`取得失敗時のランダム値へのフォールバックは不適切

`getOrCreateProfileId()`は、既存IDの読み取りにも作成にも失敗した場合、永続化できていないランダムIDを返します。

補助検証では、IDファイル位置を読み取れない状態にすると、同じプロファイルへの連続呼び出しで異なるIDが返りました。

これは表示用IDなら許容できますが、**共有プロファイルの同一性判定に使うIDとしてはfail-openです**。取得・作成・再読取のいずれも成功しなければ、プロファイル利用を停止すべきです。

同様に、`markerExists()`がすべての`stat`失敗を「markerなし」にしている点も改める必要があります。存在しない場合と、I/O障害等で確認できない場合を分離します。

## 3.8 並列化で初めて顕在化する共有設定の競合

思考量はアカウントへ永続化される前提で、各requestが変更前の値へ復元しています。

並列化すると、Aの復元がBの送信前設定を書き換える可能性があります。**Pageごとのlockだけでは足りません。別マシン・別profileでも、同一アカウントなら共有設定の競合対象です。**

推奨は、設定変更・送信直前確認・送信までを短い排他区間にし、requestごとの無条件復元をやめることです。復元する場合も、管理者が「現在の設定の所有世代」を確認し、全体がアイドルになった時点で行います。

加えて、現行の`continueButton`、`sidePanel`、`challengeFrame`の候補には`verifiedOn`がなく、既定の`verifiedOnly=true`ではselector経由の検知対象から外れます。補助検証でも該当経路がfalseになることを確認しました。CAPTCHAには別のダイアログ検知経路もありますが、**これらの安全検知が既定で有効だとは評価できません**。`--allow-unverified`を常用するのではなく、実画面で検証した候補を登録する必要があります。

# 4. 推奨アーキテクチャ

## 4.1 「常駐ブラウザ」と「ジョブ管理者」を分ける

以下は提案です。名称は責務を説明するためのもので、ディレクトリ名・型名をそのまま要求するものではありません。

```text
呼び出し元CLI／Claude Code
        │ submit / status / result / ack
        ▼
ジョブ管理サービス
  ├─ 受付・入力スナップショット
  ├─ requestIdの一意性・内容一致検査
  ├─ 永続queue・実行枠・所有権
  ├─ 回復判断・成果物確定・配送台帳
  └─ ローカルSQLite
        │ 所有権付きの実行指示
        ▼
各マシンのブラウザ担当
  ├─ profileId単位のブラウザ管理
  ├─ Pageの割当・再接続・照合
  ├─ 既存の状態機械／ChatGptPort
  └─ 回答のローカル退避・管理サービスへの転送
        │
        ▼
ChatGPT Web
```

**CLIは依頼の提出者・結果の購読者であって、生成監視の所有者ではなくなります。**

現在の`worker`を別プロセスで常駐させるだけでは不十分です。送信後timeout、再実行時のmarker拒否、回収専用経路の欠如がそのまま残るためです。

| `contracts/request.ts`、request schema | 検証部として継続利用。受付時に入力を管理領域へ固定する処理を追加                   |
| `machine.ts`                          | 送信境界、既存状態名、純関数の構造を維持                               |
| `controller.ts`                       | 実行、観測、回収、成果物確定を分離。legacy実行とmanaged実行で期限・終端ポリシーを分ける |
| `ChatGptPort`                         | 期待会話・依頼ターンを指定した観測／抽出、回収専用openを追加                   |
| `completion.ts`                       | 完了判定を再利用。managed経路では「ジョブ寿命の上限」を判定から外す              |
| `marker.ts`                           | 送信直前の永続証跡として維持・拡張。単なる再実行拒否から回復判断の入力へ発展             |
| `ProcessLock`                         | 同一マシンでの管理者・profile占有に再利用。分散ジョブleaseの代替にはしない        |
| `BrowserSession`／daemon               | profileのライフサイクル管理に利用。任意Pageの再利用・独立したkeepalive操作を廃止 |
| 抽出・Markdown変換                         | 変換処理を再利用。ただし対象は「latest」ではなく検証済みターン                 |
| `worker`のディレクトリqueue                  | 既存利用者向けの取込口として維持。内部スケジューラはDBへ移す                    |

## 4.3 守るべき不変条件

**未確認を「未送信」と解釈しない。** 送信後の不明状態は「送信済みの可能性あり」です。これは現在の`submitted: unknown`を発展させる方向であり、名称の置換ではありません。

管理層では、少なくとも以下を保証します。

* 永続的な送信意図と有効な実行許可がなければ、送信ボタンを押さない。
* 送信意図を書いた後は、クラッシュ・lease失効だけを理由に再送可能へ戻さない。
* 配送する成果物には、検証済みの依頼・会話・回答ターンの対応がある。
* `completed`は成果物commitとDB更新の後にだけ公開する。
* workerの失踪と、ChatGPT上の生成終了を同一視しない。
* 回復処理は原則読み取り専用であり、再生成・「続きを生成」・「もう一度答えて」を自動実行しない。

### 「必ず一度だけ送信」の保証範囲

ローカルDB更新とChatGPTのUIクリックを、同一トランザクションにはできません。

```text
送信意図を保存 → クリック → 送信の証拠を保存
                     ↑
               ここでクラッシュ
```

この窓では、再送すると重複する可能性があり、再送しなければ未送信のまま残る可能性があります。

したがって、今回採るべき保証は、**「不明時に自動再送しないat-most-once方針＋証拠に基づく回収・再接続」**です。「必ず送信され、しかも絶対重複しない」とは約束しない方が正確です。

同様に、まだ取得していない回答がChatGPT側から削除され、どこにも複製がない場合まで回復することは、この構成では保証できません。保証の中心は、**取得機会を失いにくくすることと、取得・commitした回答を保持すること**です。

# 5. 状態機械とrecovery path

## 5.1 実行状態とジョブ状態を分ける

現在の`StateName`を、queue・配送・ACKまで含む巨大なenumへ拡張することは勧めません。

現在の状態名はUI操作の進捗を表しており、`submitted`の不変条件もその順序に依存しています。`invariants.ts`では`STATE_NAMES`の配列位置から送信前後を導出しています。新しい状態を無造作に挿入すると、この判定まで変わります。

提案するのは次の分離です。

| 管理対象          | 状態の役割                                                           |
| ------------- | --------------------------------------------------------------- |
| 既存`StateName` | `PROMPT_ENTERED`、`GENERATING`、`EXTRACTING`等の実行フェーズ              |
| ジョブ管理状態       | `queued`、`running`、`recovering`、`blocked`、`completed`、`failed`等 |
| 配送状態          | 未配送、配送試行済み、ACK済み。ジョブ完了とは独立                                      |
| 成果物の可用性       | 正常、欠落、破損、修復中。過去の完了事実とは独立                                        |

たとえば、**ジョブは`completed`だが呼び出し元のACK待ち**、あるいは**過去に完了したジョブのローカル複製が欠落して修復中**という状態を表現できます。

## 5.2 managed実行での主遷移

```text
受付・入力固定
    → queued
    → 実行担当をclaim
    → 既存のVALIDATED〜PROMPT_ENTERED
    → 送信意図を永続化
    → PROMPT_SUBMITTING
    → WAITING_FOR_RESPONSE
    ↔ GENERATING / STABILIZING
    → EXTRACTING
    → WRITING_RESULT
    → 成果物commit
    → DBのcompleted更新＋配送待ち登録
    → 完了公開
```

既存の`WRITING_RESULT`を残し、その成功条件をmanaged経路では「結果ファイルを書いた」から「成果物とジョブ台帳を確定した」へ拡張します。既存`RESULT_WRITTEN`の意味を黙って変更せず、commit用effect／イベントを分ける方が明確です。

## 5.3 障害時の復旧

| 障害時点              | 復旧方針                                    |
| ----------------- | --------------------------------------- |
| 受付commit前         | 未受付。呼び出し元が同じrequestIdで再submit           |
| 受付済み・送信意図なし       | 古い担当の操作権を失効させた後、同じジョブをqueueへ戻せる         |
| markerあり・送信確認なし   | `recovering`。未送信と推定せず、既存会話・userターンを探索する |
| 送信済み・生成中          | 別Pageまたは再起動したブラウザから同じ会話へ接続し、観測を再開       |
| 生成完了・本文退避済み       | DOMではなく退避データから確定処理を続行                   |
| 成果物commit済み・DB未更新 | manifestとhashを確認し、DBと配送台帳を確定            |
| DB完了済み・ACKなし      | 同じ成果物を再配送する。ChatGPTへはアクセスしない            |
| 対応する会話・ターンを証明できない | `blocked`。候補を隔離保存し、配送・再送を行わない           |

**回収専用の経路を設ける必要があります。** 現在の`openConversation()`は「追記してよいか」を確認するため、生成中やassistant未出現の会話を拒否します。これをそのまま復旧に流用すると、最も回復したい生成中ジョブを開けません。送信用の厳しい条件を緩めるのではなく、読み取り専用openを別途設けます。

## 5.4 timeoutの整理

| 期限           | 期限到達時の扱い                  |
| ------------ | ------------------------- |
| CLIの待機期限     | CLIだけ終了。requestIdと現在状態を返す |
| 個々のブラウザ操作の期限 | 操作を停止・隔離し、必要なら観測担当を回復する   |
| worker lease | 担当の所有権を回復対象にする            |
| 生成時間の警告閾値    | 長時間化を記録・通知する。ジョブを破棄しない    |
| 明示的な中止要求     | 中止処理として扱う。単なる待機終了とは別      |

既存requestの`timeoutMs`を、無告知でCLI待機時間へ読み替えるのは避けます。legacy `run`の契約は残し、managed側では別の待機オプションを設け、旧`timeoutMs`の扱いを明示します。

# 6. concurrency modelと回答の照合

## 6.1 関係とlifetime

| 対象                     | 関係・lifetime                                  |
| ---------------------- | -------------------------------------------- |
| `requestId`            | 永続ジョブの主キー。CLI切断や担当交代で変わらない                   |
| 呼び出し元セッション             | 複数requestを提出できる。切断してもrequestを終了させない          |
| `conversationUrl`が指す会話 | 複数requestから順次利用できる。ただし同一会話への未解決の送信は原則1件      |
| Page／tab               | 実行・観測に一時的に借りるリソース。再起動後の正体確認には使わない            |
| browser                | `profileId`に属する起動世代を持つ。Pageを複数管理する           |
| `profileId`            | 専用プロファイルの永続識別。同一ChatGPTアカウントに複数profileが対応し得る |
| machine                | ローカルのbrowser・profile・実行容量を提供する               |
| worker                 | 一定期間ジョブを担当する実行個体。再起動時には所有トークンを変える            |

マシン登録が必要になった段階では、hostnameを表示情報として残し、別途安定した登録キーを持たせるのが妥当です。hostnameだけを恒久的な同一性や認証の根拠にはしません。

### 並列数は三つ以上の別資源として数える

「使用中のPage数」と「ChatGPTで生成中の数」は一致しません。

* 生成中だがPageを失ったジョブがある。
* 生成は終わったが保存中のジョブがある。
* 保存も終わったがACK待ちのジョブがある。

したがって、**生成枠、Page枠、browser枠を分離**します。生成枠は送信前に予約し、生成終了・停止を確認してから解放します。workerのleaseが切れただけでは解放しません。

不明な生成を枠から除外して次を開始すると、全体最大並列数の保証が崩れます。この場合は可用性を優先して推測するのではなく、枠を保持して回復・確認を待つ設計にします。

同じUser Data Directoryから複数browserを起動する構成は採用できません。複数browserを持つ場合は別の専用profileが必要です。Playwright公式にも、この制約が明記されています。([Playwright][2])

## 6.2 回答を配送してよい条件

提案する照合は、URLだけでも、assistant本文のrequestId echoだけでもありません。

**送信前**

Bridgeが管理するrequestIdの識別行を含めて、展開済みpromptを固定します。送信先、入力内容、添付スナップショット、所有権を送信直前に確認します。現行の空白全除去比較は入力欠落の検出には使えますが、依頼本文の一意な内容識別には別のhashを用います。

**送信後**

実際のuserターンに、当該requestIdと期待する本文が存在することを確認します。そのuserターンに対応するassistantターンを特定し、会話との束縛を永続化します。

**回収時**

その束縛を使い、会話、userターン、対象assistantターンを再確認します。本文、コピー、画像がすべて同じターンに属することも検証します。検証前後にPageの遷移・再描画による対象差し替えがあれば、採用しません。

実DOM上で再接続後も使える安定したmessage IDが取得できるかは、添付からは確認できません。**未知のselectorや属性を仕様として仮定せず、まず実画面で検証する必要があります。** それが得られない場合には、userターンの一意一致と回答の対応構造で証明できる範囲に限定し、曖昧な履歴は自動回収しません。

assistantによるrequestId echoは追加チェックとして有用ですが、モデルが生成する文字列なので、それ単独を正体の証明にはしません。

## 6.3 Project移動への耐性

`conversationUrl`の外部契約は維持しつつ、内部ではURLから会話部分を取り出して比較する仕組みを設けます。ただし、単に末尾IDが同じというだけで、無条件に移動後URLを受け入れることはしません。

移動を受け入れる条件は、**認めたorigin、同一会話の識別、対象userターンとassistantターンの照合**がそろうことです。新しいURLは検証済みの別表記として記録します。

ChatGPT側のProject所属が変わっても、当初のローカルproject帰属やarchive配置を自動的に変更する必要はありません。

## 6.4 leaseだけでは古いworkerのUI操作を止められない

DBへの更新は所有トークンと世代番号を条件に拒否できます。しかし、ChatGPTの送信ボタンはその世代番号を検証しません。

したがって、**lease失効後に新workerへ送信権を渡す前に、古い担当がPageを操作できないことを保証する必要があります。** 原則として、各profileのブラウザ操作は単一の管理者だけが行い、外部workerが自由にCDP接続する構成をやめます。

古い担当を停止・切断できない場合には、送信権を再割当しません。読み取り回復やローカル退避と、新しい送信許可は分けて扱います。

# 7. persistence設計とcommit boundary

## 7.1 正本を三重化しない

推奨する責務分担は次のとおりです。

| 保存物                    | 正本として担当する情報                        |
| ---------------------- | ---------------------------------- |
| `prompt.md`・添付スナップショット | 実際に送信対象として固定した入力                   |
| `response.md`・画像       | 採用した回答の内容                          |
| `meta.json`            | 成果物の依頼帰属、会話束縛、相対パス、hash、commitの証拠  |
| SQLite                 | ジョブ状態、担当、lease、queue、配送・ACK、イベント履歴 |
| `submit.marker`        | 送信意図・送信境界の永続証跡                     |

重要なのは、**SQLiteに実行中状態やACKを持たせるなら、DBは単なる捨てられるindexではない**という点です。

MD群から成果物indexは再構築できます。しかし、回答未取得のジョブ、送信直前の不明状態、配送済みか否かまで、回答MDだけから復元することはできません。DBのバックアップと送信台帳の保持が必要です。

## 7.2 ディレクトリ構造

既存名称を活かすなら、次の程度で十分です。

```text
<archiveRoot>/
  <localProjectKey>/
    2026/
      09/
        <requestId>/
          request.json
          prompt.md
          attachments/
          response.md
          images/
          result.json
          meta.json
```

`request.md`への改名は不要です。既存の`prompt.md`と`request.json`を残します。

運用上project別の階層が不要なら、`<archiveRoot>/requests/<requestId>/`でも成立します。**正確性を階層名に依存させない**ことが重要です。

年月は受付日時から決め、一度決めた保存位置は実行状態が変わっても移動しません。DBには`archiveRoot`からの相対パスを保存します。ローカルprojectの表示名変更でも、既存ディレクトリを自動renameしない方が堅牢です。

既存`result.json.responseFile`の絶対パスは互換出力として残せますが、新しい取得処理はその古い値を権威にせず、manifestと現在のarchive rootから解決します。

## 7.3 受付のcommit

受付時点で、promptだけでなく添付も管理領域へコピーし、内容を固定します。現行実装は添付を検証した後、その絶対パスを保持するため、受付から実行まで長く待つ設計では元ファイル変更の影響を受けます。

提案する受付手順は次です。

```text
入力検証
 → 管理領域へprompt・添付を固定
 → 実際のバイト列のhashを確定
 → DBへrequestId・入力識別・queue登録をcommit
 → 受付済みを返す
```

同一requestIdで同一入力なら既存ジョブを返し、異なる入力なら競合として拒否します。待機時間や取得先パスの違いは、新しい質問とは扱いません。

並列上限を超えた依頼はqueueへ入れますが、不正入力、保存容量不足、永続化失敗まで無条件に受け付けるべきではありません。**受付完了と返した後に、実は入力を保持していなかった状態を作らない**ことが優先です。

## 7.4 回答のcommit

ファイルとSQLiteを同時にatomic commitするのではなく、**途中状態を再処理できる順序**にします。

```text
1. 対象会話・依頼・回答ターンを検証
2. 本文をstagingへ即時保存・同期
3. 画像等を処理し、最終成果物を確定
4. 保存した実バイト列のhashを計算・検証
5. response.md、result.json等を確定
6. meta.jsonを最後に確定し、成果物commitを示す
7. DBでcompleted更新と配送待ち登録を同一transactionでcommit
8. 呼び出し元へ完了を公開
```

stagingは内部の回復用領域です。未確定データを、通常の`result`コマンドが完成回答として返してはいけません。

また、古いworkerが最終`response.md`を上書きできないようにします。workerは担当世代ごとの候補領域へ書き、最終公開は所有権を再確認した管理者だけが行います。

### クラッシュ位置別の扱い

| 残った状態                  | 復旧                            |
| ---------------------- | ----------------------------- |
| stagingのみ              | 帰属と完全性を確認し、確定処理を続行する          |
| MDあり・commit manifestなし | 完成回答として返さず、記録された証拠から確定可能か判断する |
| manifestあり・DB未完了       | hash確認後、DBと配送台帳を修復する          |
| DB完了・MD不在              | 通常配送を停止し、ローカル探索・複製復元を開始する     |
| 完了通知直後にcaller切断        | 完了状態は維持し、同じ成果物を再取得できるようにする    |

現行の一時ファイル＋fsync＋renameは有用ですが、ファイル名の切替と停電後の永続性は同義ではありません。Unixではディレクトリ同期まで考慮する必要があり、Windowsを含む対応filesystemについて実証すべきです。SQLite自身も、停電時のファイル出現を保証するためにディレクトリ同期を扱っています。([SQLite][3])

## 7.5 DBの最小構成

最初から多数の独立サービスや複雑なイベントソーシング基盤は不要です。概ね次の責務があれば足ります。

| 管理単位      | 主な情報                                                                            |
| --------- | ------------------------------------------------------------------------------- |
| jobs      | requestId、固定入力の識別、呼び出し元、ローカルproject、状態、実行フェーズ、submitted、conversationUrl、成果物相対パス |
| 実行・所有権    | 担当マシン、profileId、所有トークン、世代、lease期限、heartbeat                                     |
| 重要イベント    | 受付、送信意図、送信証拠、会話束縛、保存、失敗・回復判断                                                    |
| 配送        | requestId、受領者、成果物識別、配送試行、ACK                                                    |
| project登録 | ローカルprojectキー、既存`project`のURL、マシンごとのリポジトリ設定、archive方針                           |

250msごとの観測をすべてDBへ書く必要はありません。現行controllerも履歴を最大4,000件に制限しています。ただしこれはメモリ上の完了判定用履歴であり、復旧用checkpointではありません。永続化するのは束縛、送信証跡、重要な状態変化、回復に必要な要約です。

## 7.6 hashとローカル復旧

hashは採用します。過剰設計ではありません。ただし用途を区別します。

* 入力hash：同一requestIdの内容変更を検出する。
* 回答・画像hash：保存後の破損や別ファイルへの差し替えを検出する。
* manifestの識別：配送・ACKがどの成果物に対するものかを固定する。

hashは**実際に保存したバイト列**から計算します。現行の観測用SHA-1や`verifyCandidate()`を流用して、同等の保証があるとは扱いません。現行抽出検証は単語被覆率による比較であり、順序・記号・全バイトの一致検証ではありません。

MDが見つからない場合は、要求どおり次の順序を採ります。

```text
既知の相対パス
 → 登録済みarchive root・移動先
 → requestIdとmanifest、期待hashによる再発見
 → 他のローカル複製・バックアップ
 → DBの保存場所を修復
 → それでも無ければ検証済み会話から読み取り専用で再回収
```

再回収した本文が以前のhashと異なる場合は、同じ正本として黙って置き換えません。抽出方式の変化、会話編集、別ターンの可能性があるため、新しい候補として隔離します。

DB喪失時も同様です。再indexだけで全ジョブを「未送信」に戻してはいけません。**送信台帳・各担当の記録と照合できるまで、新規送信を止める復旧モード**が必要です。

# 8. multi-machine方式の比較と最終推奨

| 案                                  | 信頼性・復旧                            | 複雑さ・運用                | filesystem／locking依存     | 裁定                  |
| ---------------------------------- | --------------------------------- | --------------------- | ------------------------ | ------------------- |
| 各マシンに独立DB・独立queue                  | 単体では復旧しやすい。端末間の同一ID・全体上限は別途協調が必要  | 初期は低いが、後から同期すると複雑化する  | ローカルFS中心                 | 独立運用には可。今回の全体管理には不足 |
| **単一管理サービス＋そのホストのSQLite＋各端末agent** | 共通台帳で重複・枠・担当を統制できる。停止後の照合もしやすい    | 中程度。サービスの起動・バックアップが必要 | DBはローカルFS。端末間はアプリケーション通信 | **推奨**              |
| 管理サービス＋PostgreSQL等                 | DBの可用性・運用拡張を進めやすい。UI側の不明送信問題は別途残る | 個人用途では初期コストが高い        | DBのネットワークプロトコルを利用        | 将来候補。最初からは不要        |
| SMB等の共有SQLiteを各端末が直接操作             | 共有FSのロック・同期・障害挙動へ依存する             | 見かけは簡単だが、障害解析が重い      | 強い                       | **不採用**             |

SQLite公式は、WALを利用する全プロセスが同一ホスト上にいる必要があるとしています。また、ネットワーク越しに利用する場合の選択肢として、DBと同一ホストで読み書きするproxy方式を示しています。今回の推奨構成は、この方式に相当します。([SQLite][4])

### 推奨構成の運用上の条件

**中央不通時にローカル独断で新規送信しない。** 既に実行許可を受けて生成中のジョブは、ローカル退避を続けられるようにしますが、新しい送信許可は中央なしで発行しません。

browser、profile、`node_modules`はマシンごとに独立させます。CDPは各ホストのループバック内に留め、中央サービスから無認証CDPをネットワーク公開する構成にはしません。現在のローカルCDP無認証は、単一の信頼された利用者という前提で許容された残存リスクです。ネットワーク境界を追加するなら、その前提を引き継げません。

回答はまず実行マシンのローカルspoolへ退避し、中央archiveへ転送します。中央archiveのMDを管理上の正本とし、各マシンのMDは同じhashを持つ複製として扱います。

「マシンが落ちても」がディスクを保持した再起動を意味するのか、ディスクそのものの永久喪失まで含むのかは、保証として区別します。後者まで保証する場合は、**回答と必要な台帳が独立した保存先へ複製されたことを確認してから、その耐久性を満たしたと通知する**必要があります。

SQLiteはローカルWALを基本とし、今回の用途では`NORMAL`より`FULL`を優先します。`NORMAL`ではOSクラッシュ・停電後にcommit済みtransactionが失われる可能性が公式に説明されています。([SQLite][5])

バックアップは稼働中のDBファイルを単純コピーするのではなく、Online Backup API等を使用します。([SQLite][6])

導入時には実際に組み込まれるSQLite版も確認してください。現在の公式文書には、複数接続のWAL書込・checkpoint競合に関係するWAL-reset bugと修正版が記載されています。今回のbundleにはSQLite依存自体がないため、利用予定のbindingが修正版を含むかは未確認です。([SQLite][4])

# 9. 段階的migration、delivery／ACK、CLI UX

## 9.1 実装順序

| Phase                     | 実装する範囲                                                                    | 次へ進む条件                            |
| ------------------------- | ------------------------------------------------------------------------- | --------------------------------- |
| **0：現行の危険窓を縮小**           | 回収時の会話束縛検証、queue単一管理者、profileId取得失敗の停止、closeとkeepaliveの所有権整理、安全selector確認 | 別会話採用、稼働中queue移動、ID取得失敗の検証が通る     |
| **1：単一マシン・並列数1のdurable化** | 入力スナップショット、DB受付、status/result、CLI寿命分離、本文即時退避、成果物commit                    | CLI切断・長時間生成・管理サービス再起動後に同じIDで取得できる |
| **2：送信後の回復**              | 読み取り専用Recovery、会話・ターンの永続束縛、marker／manifest／DB照合                           | 各送信・保存境界で落としても、再送せず回復または明確に保留できる  |
| **3：同一マシンの並列化**           | Page割当、複数caller、会話排他、生成枠、設定変更の排他、trace管理                                  | タブ入替・消失・担当失効で誤配送しない               |
| **4：複数マシンと配送強化**          | 中央管理、端末登録、全体枠、転送・複製、ACK、障害時の再配送                                           | 端末間切断・再接続・同一ID同時submit・旧担当復帰を通過   |

Phase 1の時点で、最小のhelp・template展開・短い利用手順も整備して構いません。安全性と無関係なUX改善を最後まで待たせる必要はありません。

### 移行中の重要な禁止事項

**managedモードの管理対象profileへ、旧`run`が管理サービスを迂回して接続するフォールバックを残さないこと。**

サービス不通時に旧経路で勝手に送信すると、全体の重複防止と所有権が崩れます。旧経路は別profileで維持するか、管理サービス経由の互換コマンドにします。

既存データは、稼働中writerを止めてからimportします。元の`request.json`、`result.json`、markerは保持し、後から推定したcallerやmachineを「元から分かっていた事実」として埋めないようにします。不明項目は不明のままです。

## 9.2 delivery／ACK

ACKは採用する価値があります。ただし、保証するのは**呼び出し元のadapterが対象の成果物を永続的に受領したこと**です。LLMが回答を読んだ、理解した、実装へ反映したことまでは証明しません。

推奨手順は次です。

```text
Bridgeの完了commit
 → 配送待ち台帳へ登録
 → caller adapterが取得
 → caller側へatomic保存
 → requestId・成果物識別・hashを確認
 → adapterがACK
```

ACKはLLMへ文章生成させず、CLI protocolで送ります。受領者と成果物の版が接続文脈で一意なら、wire上の`ACK <id>`程度でも構いません。ただし複数の受領者が存在するなら、内部では**誰が、どの成果物を受領したか**を識別する必要があります。

stdoutへの出力成功を自動ACKにしてはいけません。パイプの先や呼び出し元が、その直後に落ちる可能性があるためです。

ACK喪失時は同じ成果物を再配送し、caller側で重複排除します。ACKを受けたことを理由に正本を即削除する設計にもすべきではありません。

## 9.3 templateと`preset`の衝突を避ける

用途別テンプレートは賛成です。ただし、要求例の次の形は採用しません。

```yaml
preset: code-review
```

既存の`preset`は思考量です。ここへ用途を混ぜると、既存契約と衝突します。**用途は`template`、思考量は既存の`preset`のまま**にします。

また、テンプレート資産そのものは既に文書化されています。`prompts/code-review.md`等を活かし、呼び出し側が行っている展開をBridge側へ移すのが自然です。添付には各テンプレート本文がないため、その品質まで評価したわけではありません。

上位入力の例は次の形です。

```yaml
template: code-review
target: context.md
focus:
  - functional bugs
  - concurrency
preset: high
```

これを既存`BridgeRequest`と展開済み`prompt.md`へ変換します。厳格な既存request schemaへ、便利だからと多数の用途別フィールドを直接追加する必要はありません。

テンプレート名、版またはhash、展開後promptを保存します。同じrequestIdへの再submitでは、最新テンプレートで再展開せず、最初に固定した入力へ接続します。

なお、この方式が減らすのは主に**呼び出し元LLMが定型文を毎回生成する負担**です。ChatGPTへ送る展開後prompt自体が短くなるわけではありません。

## 9.4 CLIの推奨形

以下は新機能の提案であり、現行コマンドではありません。

```text
chatgpt-bridge --help
chatgpt-bridge template
chatgpt-bridge template code-review

chatgpt-bridge submit --request request.json --json
chatgpt-bridge status <requestId> --json
chatgpt-bridge wait <requestId> --timeout-ms 30000 --json
chatgpt-bridge result <requestId> --out response.md --json
chatgpt-bridge queue --json
```

`submit`の成功は受付完了、`wait`の成功はジョブ完了、と明確に分けます。旧`run`の「exit 0＝completed」と混同させません。

既定helpは短いコマンド索引と安全上の要点だけにし、詳細はサブコマンドhelpへ分離します。現行でも毎回helpを出しているわけではなく、主に`--help`、引数なし、未知コマンド時の出力です。そこを改善すれば十分です。

`USAGE.md`には、「submitしてIDを保持」「待機終了は再送理由にしない」「resultを取得」の最小手順を載せます。`CLAUDE.md`等への追記は、明示的な初期化コマンドで短い参照行だけを書き、起動のたびに自動変更しない設計を勧めます。

# 10. テスト戦略と受入条件

## 10.1 テストを三層に分ける

**純関数・フェイクポート試験**では、状態遷移、所有権、期限、配送、commit境界を検証します。長時間生成は仮想時計で進めます。現在のcontrollerには実`setTimeout`も含まれるため、期限処理をClock経由へ整理すると、待たずに試験できます。

**ローカルの模擬ChatGPT画面によるブラウザ試験**では、会話遷移、DOM再描画、タブ消失、同じ件数を持つ別会話、コピー対象の入替を再現します。模擬サーバ側で生成を継続させることで、ブラウザを落としても後から回収できる条件を作ります。

**実機・chaos試験**では、Windows／Macでプロセスkill、スリープ・復帰、ブラウザ強制終了、ネットワーク分断、保存先のアクセス障害を確認します。プロセスkill試験と停電・filesystem障害試験は同等ではないので、後者は別枠で評価します。

## 10.2 シナリオ別の期待結果

| 試験                            | 必須の期待結果                            |
| ----------------------------- | ---------------------------------- |
| タブ順序変更・別タブへの割当ミス              | ページ番号に依存せず、照合不一致なら配送しない            |
| 会話Aから同じassistant件数のBへ遷移       | BをAの回答として採用しない                     |
| 検証直後のnavigation・DOM再描画        | 古い検証を使って新しいDOMを採用しない               |
| 同一会話に人間が別requestを追加           | 元requestの回答を特定するか、曖昧として保留する        |
| tab消失                         | 同じ会話・requestへ再接続し、送信せず観測を再開        |
| browser crash                 | 影響した全ジョブを回復対象にする。新規送信と回収を混同しない     |
| daemon／管理サービスcrash            | 再起動後にclaim、marker、manifest、DBを照合する |
| CLI timeout／caller disconnect | ジョブを失敗・削除・再送しない                    |
| 26分、60分を超える生成                 | 待機CLIの寿命に関係なく、完了後に回収する             |
| 同一ID・同一入力の重複submit            | 既存ジョブを返す。送信クリックは増えない               |
| 同一ID・異なる入力                    | 明示的な競合。既存入力・結果を変更しない               |
| 複数caller・複数machine            | 帰属と結果が混ざらず、全体枠を超えない                |
| lease失効後に旧workerが復帰           | DB更新・成果物公開・UI操作のいずれも旧所有権では許可しない    |
| 本文保存後・manifest前にkill          | 未確定回答を返さず、同じ取得データから回復する            |
| manifest後・DB前にkill            | DBと配送台帳を修復し、再生成しない                 |
| DB上は完了、MD削除・移動・破損             | hashとmetadataでローカル復旧を優先する          |
| ChatGPT会話削除・Project移動         | 保存済み回答は利用可能。未取得回答は厳密照合または保留        |
| ACK喪失・重複ACK                   | 同一成果物を再配送可能。ACK処理は冪等               |
| `EACCES`／`EIO`等               | 「ファイルなし」「lockなし」「未送信」に読み替えない       |
| 画像取得・close・CDPが停止しない          | 本文退避を失わず、古い操作が新担当へ干渉しない            |

### 特に必要な契約統合試験

A-112では、controllerのテストが`writeResult`をfakeしていたため、結果schemaとの不一致を見逃した経緯が記録されています。今後は、**実際の`fileContracts()`、実schema、実一時ディレクトリを使った試験**を必須にしてください。

「controllerがcompletedを返した」だけでは合格にせず、実際に保存されたMD、manifest、DB、JSON出力が同じ依頼・同じ成果物を指していることまで確認します。

# 最終判断

**今回の要求は、現在の「薄いブリッジ」を否定するものではなく、その外側に必要な責務が増えたものとして扱うのが適切です。**

ただし、次の四つの安易な拡張は避けるべきです。

* `bridge.lock`を外して、既存`run`を並列起動する。
* ACTIVE timeoutをさらに長くするだけで、回答喪失対策とする。
* `conversationUrl`とrequestId echoを保存するだけで、対応関係を証明したとする。
* SQLiteを共有ドライブへ置いて、複数マシン管理を実現したとする。

最初の到達点は、**「並列数1のまま、CLIを終了してもジョブが残り、再起動後に同じrequestIdの回答を再送なしで回収できる」こと**です。

そこまでできれば、並列化は新しい安全機構をその場で作り足す作業ではなく、**確立した所有権・束縛・保存の仕組みへ、複数の実行枠を与える作業**になります。この順序が、既存設計を最も活かしながら事故を減らす進め方です。
